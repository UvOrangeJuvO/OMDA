## Findings

### [P1] G0-001 — Port contracts are scheduled after the Orchestrator that requires them

- Location: `governance/IMPLEMENTATION_PLAN.md`, B.3/B.9, T2.6 and T3.1 (approximately lines 105–142, 267–297)
- Evidence: the architecture states that the Orchestrator invokes adapters through Ports, but the plan does not define the six Port interfaces and domain error taxonomy until G3/T3.1. G2/T2.6 already intends to implement the full run state machine, including generation, delivery, journal/history commit and recovery. That implementation cannot be built and contract-tested cleanly before the required application boundaries exist.
- Impact: G2 would either depend directly on concrete G1 SQLite/storage code, invent private ad-hoc interfaces and later refactor them in G3, or implement an untestable skeleton. All three outcomes undermine the declared inward dependency direction and make the highest-risk Gate unstable.
- Violated contract: `OMDA_AGENT_HANDOFF_SPEC.md` §3.1–3.2 and §10; Master Plan §4; the candidate's own B.2/B.3/B.9.
- Required correction: move the **minimal application Port protocols and domain error taxonomy needed by G2** to G1 or the beginning of G2, before any Orchestrator work. G2/T2.6 must run entirely against fakes/in-memory test implementations of those contracts. G3 should implement concrete external data/browser adapters and may refine source-specific contracts only through normal Gate review; it must not be the first point at which the Orchestrator's essential boundaries exist.
- Acceptance test for closure: the revised task dependency graph has no G2 task depending on a contract first delivered in G3, and explicitly states how G2 exercises `GENERATE`, `DELIVER`, journal and history transitions with fakes while concrete LLM/PushPlus/RYM adapters remain later work.

### [P1] G0-002 — The pure Recommendation Core is described as reading runtime history/storage

- Location: `governance/IMPLEMENTATION_PLAN.md`, T2.4 dependency and T2.6 rollback (approximately lines 247–278)
- Evidence: T2.4 lists `T1.4（history 读取）` as a dependency for Album filtering even though B.1 promises a pure Core with no database driver or persistence implementation. T2.6 then says runtime data under `var/` can be reset as rollback.
- Impact: the first statement permits persistence concerns to leak into Album selection; the second is unsafe once `var/` contains official local history or recovery evidence. Deleting/resetting runtime data is not a valid rollback for user state.
- Violated contract: `OMDA_AGENT_HANDOFF_SPEC.md` §3.1, §3.3, §4 and §9; Master Plan §4 Storage and §6; `AGENTS.md` non-negotiable history and destructive-action rules.
- Required correction: state that the Application Orchestrator/History Port reads a versioned history snapshot or exclusion set and supplies it as an immutable domain input to Core. Core must not read SQLite, `HistoryStore`, or files. Replace the `var/` reset rollback language with a distinction between disposable test databases and protected real runtime data; real state requires backup/migration/recovery or a non-destructive compensating procedure.
- Acceptance test for closure: the plan requires an architecture test proving no persistence imports/calls from Core, includes a unit test that supplies historical exclusions as input, and contains no instruction that treats real runtime history as safely deletable.
